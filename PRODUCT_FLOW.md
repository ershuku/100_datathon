# Как должен работать продукт Datathon

Это целевое поведение, а не отчёт о готовой реализации. Основной план и роли — TEAM_PLAN.md; правила ИИ — AGENTS.md. Источник требований — исходное ТЗ ForteBank. Ниже обязательные требования отделены от предлагаемых способов реализации.

## 1. Два входа, один анализатор

Сайт нужен человеку, API — автоматической проверке жюри. Оба используют одну версию локального pipeline и один контракт результата. Один job_id показывает один сохранённый результат через оба интерфейса. При отдельных стохастических запусках результаты могут отличаться.

Путь пользователя: открыть сайт → выбрать `.mov` → загрузить → дождаться обработки → увидеть вердикт и все события с доказательствами.

Путь жюри: POST с файлом и ключом → получить job_id → опрашивать GET с ключом → получить итоговый JSON.

## 2. Загрузка через сайт

Обязательно: веб-интерфейс и сервер, приём видео, отображение статуса, результат без ручного запуска кода (§4–5 ТЗ). Регистрация, пользовательская история, экспорт и пакетная загрузка не требуются по FAQ.

Рекомендуемый экран: описание назначения, выбор/перетаскивание файла, указание формата `.mov`, кнопка начала проверки. Реальный прогресс передачи файла можно показывать отдельно от анализа.

Сервер проверяет читаемость контейнера, поддерживаемый формат, размер и параметры, доступные ресурсы. Ограничения должны принимать ожидаемые по ТЗ ролики около 29 МБ; проверка расширения сама по себе недостаточна. Повреждённый файл — техническая ошибка, а не отсутствие нарушения.

## 3. Задание и статус

Сервер безопасно сохраняет файл, создаёт job_id, связывает его со статусом, временем, результатом или ошибкой. Конкретная БД и механизм очереди — решение команды, не требование ТЗ.

Тяжёлый анализ выполняется отдельно от короткого HTTP-запроса. Не принимать неограниченное число заданий при исчерпании ресурсов. Ожидание в очереди входит в бюджет обработки.

Для сайта рекомендуются понятные реальные этапы: подготовка → анализ → проверка событий → подготовка результата. Если точный процент неизвестен, не рисовать выдуманный прогресс. Сайт периодически получает состояние задания.

## 4. Анализатор — предлагаемая архитектура

1. Декодировать видео, определить длительность и сохранить соответствие кадров исходным таймкодам.
2. Просмотреть весь ролик локальной моделью, выделить потенциальные интервалы. Не ограничиваться одним событием.
3. Уточнить действия, границы и конкретный доказательный момент на выбранных интервалах. Контролировать риск пропуска коротких событий быстрым проходом.
4. Сопоставить наблюдение с проверенным каталогом типов и нормативных оснований РК. Не придумывать источник, пункт или невидимые обстоятельства.
5. Выбрать 1–3 исходных JPEG-кадра на событие: при необходимости до/во время/после действия. Их время должно соответствовать исходному видео.
6. Сформировать структурированный результат и проверить его схему.

Последовательность алгоритма — рекомендация команды. ТЗ требует качество результата, не конкретную модель или обязательное дообучение.

Все модели исполняются внутри развёрнутого командой сервиса. После подготовки весов обработка не требует интернета. Нельзя передавать облачным AI видео, кадры или их описания. Звук и идентификация лиц запрещены.

## 5. Вердикт и ошибки

- `no_violation`: признаки нарушения не обнаружены, violations пустой.
- `violation`: найдено хотя бы одно предполагаемое нарушение, violations содержит все обнаруженные события.
- Технический сбой: status failed. Не превращать ошибку декодирования/модели в no_violation.

Третий verdict не добавлять без разъяснения организаторов: основной контракт допускает только два, хотя FAQ упоминает недостаточность данных. Не делать категоричных юридических выводов при недостаточной видимости; правила должны учитывать границы наблюдения.

## 6. Экран результата

При отрицательном результате: «Нарушение не обнаружено». Это не гарантия корректности всех невидимых банковских операций.

При положительном: «Обнаружены признаки возможных нарушений». Для каждого события отдельно показать:

- тип;
- таймкод;
- 1–3 доказательных кадра;
- описание наблюдаемого действия и почему оно может указывать на нарушение;
- нормативное основание: документ, пункт/раздел при наличии и ссылка.

Это обязательное содержание по §4–6. Кнопка перехода к моменту в видеоплеере — полезное дополнительное удобство, не отдельное требование конкурса. Результат помогает проверке человеком, а не устанавливает вину, намерение или окончательный юридический факт.

## 7. API жюри — обязательный контракт §10

### Шаг A: загрузка

```bash
curl -X POST https://team.example.kz/api/v1/analyze \
  -H "X-API-Key: <ключ-жюри>" \
  -F "file=@video.mov"
```

Ответ содержит job_id:

```json
{"job_id":"3f2a9c1e"}
```

URL в примере — заглушка. В реальной сдаче передаётся рабочий публичный адрес.

### Шаг B: опрос

```bash
curl https://team.example.kz/api/v1/jobs/3f2a9c1e \
  -H "X-API-Key: <ключ-жюри>"
```

Пока обработка идёт, status — processing; после завершения — done; при сбое — failed. Минимальный пример промежуточного ответа (ТЗ задаёт статусы, но не исчерпывающую схему промежуточных ошибок):

```json
{"job_id":"3f2a9c1e","status":"processing"}
```

Успешный ответ без событий:

```json
{
  "job_id": "3f2a9c1e",
  "status": "done",
  "verdict": "no_violation",
  "violations": []
}
```

Шаблон ответа с событием — не реальная разметка и не готовый рабочий ответ:

```json
{
  "job_id": "3f2a9c1e",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Согласованный тип события",
      "timecode_sec": 44.2,
      "description": "Наблюдение, основание вывода, проверенный документ и пункт.",
      "evidence_frames": [
        {"timestamp_sec": 44.2, "image_base64": "<реальный JPEG в base64>"}
      ]
    }
  ]
}
```

При нескольких событиях — несколько объектов в violations; на каждый 1–3 JPEG-кадра в base64. В реальном ответе подставляется содержимое изображения, а не путь, URL или строка-заглушка.

Отдельного поля источника в примере ТЗ нет, хотя нормативное обоснование требуется. До уточнения можно помещать проверенный документ/пункт в description, а в UI показывать ссылку. Не требовать от жюри дополнительных заголовков или полей, отсутствующих в контракте.

X-API-Key проверяется на обоих маршрутах; запросы без правильного ключа отклоняются. Секрет нельзя коммитить или встраивать в публичный frontend. Для UI выбирается безопасная серверная схема доступа без обязательного личного кабинета.

## 8. Срок, устойчивость и хранение

Если сервис недоступен или не вернул результат за пять минут, видео считается необработанным (§10). Точка начала отсчёта в ТЗ не уточнена; как консервативный критерий команды внутренний бюджет измерять от внешнего запроса до готового ответа: загрузка, очередь, декодирование, inference и упаковка. Короткое время inference отдельно не доказывает соблюдение лимита.

При failed сайт показывает понятную ошибку; внутренний технический журнал не содержит ключей, кадров и описаний банковских событий. Пользователь может повторить корректный запрос; бесконечные автоматические повторы недопустимы.

Временные видео, кадры, результаты и кэши имеют срок хранения и удаление. Конкретная политика — инженерное решение с учётом условий конкурса. Тест жюри не используется для обучения или последующей настройки, не публикуется и не передаётся третьим лицам. Кэш не должен подменять анализ заранее сохранёнными эталонными ответами.

## 9. Границы участников

| Часть | Владелец |
|---|---|
| Первичная разметка и согласованные наблюдения | Бага и Ершуак |
| Каталог источников и условий правил | Бага, независимая проверка Ершуака |
| Локальная модель, действия, типы, время, выбор кадров | Айбар |
| Загрузка, задания, API, сериализация кадров, UI, сервер | Четвёртый участник |
| Независимая проверка обнаружения и полного сценария | Ершуак, исправления соответствующими владельцами |

Стык: четвёртый передаёт анализатору локальный путь к файлу; Айбар возвращает валидируемые данные событий и выбранные кадры. Внутренний интерфейс согласовать до параллельной реализации. У четвёртого нет обязанности придумывать типы/правила; Айбару не нужно повторно писать его frontend/backend.

## 10. Что считается первым рабочим продуктом

На новом разрешённом ролике сайт и API используют настоящий локальный анализатор и возвращают согласованный результат с проверяемыми кадрами. Проверены отрицательное видео, событие, несколько событий при наличии подтверждённого примера, повреждённый ввод, неверный ключ и технический сбой. Mock-режим отключён для реальной сдачи.

Отдельно измерены время, ложные тревоги, пропуски и ошибки классификации/локализации. Доступен публичный URL, подготовлены API-ключ для жюри, инструкции, архитектура, модели, нормативные источники, типы и ограничения (§8). Это критерии нашей приёмки, а не подтверждение уже выполненной реализации или гарантированных баллов.

Уточнения: timecode_sec и timestamp_sec считаются от начала исходного видео. Ошибка загрузки до создания задания может возвращаться без job_id; failed относится к созданному заданию. Этапы UI не заменяют внешние processing/done/failed. FAQ допускает источники без точного пункта; проверенный точный пункт предпочтителен.
