# Конечный автомат нарушений (rule engine): описание для ревью

Статус на 18.10.2026: первая рабочая версия. Правила подобраны **только на train-роликах**, проверены на validation, test не смотрели. Документ нужен для ревью идеи и для планирования следующей модели (детектор/трекер).

## 1. Место в системе

```
видео (.mov)
  └─ detector.py   RF-DETR, 5 кадров/с, одна рамка на мебель   → кадры в формате трекера
       └─ rules.py  сигналы кадра → сглаживание → события → правила → нарушения
            └─ analyzer.py  DetectedEvent для бэкенда (тип, таймкод, описание, 1–3 момента-доказательства)
                 └─ бэкенд  кадры-доказательства, текст нормы из config/rules_legal.yaml, ответ API
```

| Файл | Что внутри |
|---|---|
| `src/pipeline/rules.py` | Весь автомат: сигналы, сглаживание, правила, русские описания, `evaluate()`. Чистый Python, без GPU |
| `src/pipeline/detector.py` | Детектор по видео → кадры (PyAV, `pts_sec` из декодера, рамки в пикселях исходника) |
| `src/pipeline/analyzer.py` | `create_analyzer()` для `PIPELINE=real`; веса из `DETECTOR_WEIGHTS`, без сети |
| `tests/test_rules.py` | 15 тестов на синтетических сценах (без видео и модели) |
| `training/eval_rules.py` | Сравнение с разметкой организаторов: вердикт и таймкод, test-ролики не оценивает |
| `training/rule_timelines.py` | Посекундные таймлайны сигналов для отладки |

Правило не придумывает нормативную ссылку: оно возвращает только код типа (`ID`, `SAFE`, …). Документ и пункт подставляет бэкенд из `config/rules_legal.yaml`, который заполняют люди. Сейчас там везде TODO, поэтому ссылок в ответе пока нет.

## 2. Вход

Тот же JSON, что получает трекер: `frames[]` с `pts_sec`, `width`, `height`, `detections[{label, score, box_xyxy}]`. Классы детектора: `person, cash_stack, cash_bag, id_card, keys, safe_open/closed, laptop_open/closed, door_open/closed, counter_machine, uv_detector, journal, scissors, personal_item`.

## 3. Сигналы кадра

| Сигнал | Как считается |
|---|---|
| `people` | Число рамок `person` со score ≥ 0.5. Рамка, лежащая на ≥ 50% внутри уже учтённой, считается тем же человеком. Отражения в стекле обычно имеют меньший score |
| `door`, `safe`, `laptop` | Состояние open/closed лучшей рамки семейства; `None`, если не видно |
| `desk_zone` | Медианная рамка вокруг счётной машинки и ноутбука по всему видео, расширенная на 60%. Камера неподвижна, поэтому зона одна на видео |
| `cash_desk` | Число пачек денег в зоне стола, не внутри машинки и не внутри сейфа |
| `cash_counter` | Пачка на ≥ 50% внутри рамки машинки (+15%) |
| `id_card`, `bag`, `journal` | Есть ли объект (сумка и журнал — только в зоне стола) |
| `personal_desk` | `personal_item` со score ≥ 0.55 в зоне стола |
| `keys_in_safe` | Рамка ключей касается рамки сейфа |

**Почему не фильтр «человек внутри рамки двери»:** с верхней камеры дверь находится за спиной кассира. Рамка двери (x 0–236) накрывает кассира (x 109–214) почти на каждом кадре, и такой фильтр выкидывал реального кассира.

## 4. Сглаживание: это не дедлайны

Скользящее окно ~1 с (5 кадров): большинство для состояний и флагов, медиана для счётчиков. `DEBOUNCE_FRAMES = 5` — это подавление мерцания детектора, а не правило. В самих правилах нет таймеров вида «деньги на столе 10 секунд» (Aibar.md, принцип 3): все сроки — события.

## 5. Роли и визиты

- `people == 0` — комната пуста; `1` — кассир один; `≥ 2` — кассир с клиентом (или инкассатором).
- **Визит клиента** — непрерывный отрезок `people ≥ 2`.
- **Уход кассира** — переход `≥ 1 → 0`. **Вход** — `0 → ≥ 1`.
- Конец ролика — не уход и не завершение операции: незакрытые обязательства считаются «в процессе» и не дают нарушения.

Это самая слабая часть автомата: одна пропущенная рамка человека разрывает визит (см. §8).

## 6. Правила

Каждое правило работает независимо, одно нарушение не подавляет другие. `needs_review = True` означает «требует проверки»: при `REVIEW_POLICY=report` событие всё равно попадает в ответ.

| Код | Обязательство → дедлайн (событие) | Когда нарушение | Таймкод | Review |
|---|---|---|---|---|
| `ID` | Удостоверение → до приёма денег/сумки | В визите появились деньги (рост `cash_desk`, деньги в машинке или сумка), а `id_card` ещё не было | момент приёма | да, если клиент виден < 1 с до приёма или ID появился только после |
| `INCOMPLETE` | Пересчёт и сейф → до ухода клиента | Клиент ушёл, деньги на столе и сейф после приёма не открывался; или клиент ушёл во время пересчёта | момент ухода | нет |
| `TABLE` | Деньги клиента A убраны → до входа клиента B | Начался следующий визит, а на столе деньги прошлого | вход B | нет |
| `SAFE` (пересчёт) | Сейф закрыт → до начала пересчёта после выемки | Пересчёт **начался**, когда сейф уже был открыт (в момент открытия машинка пуста) | начало пересчёта | нет |
| `SAFE` (уход) | Сейф закрыт, ключи забраны → до ухода | Сразу после ухода сейф открыт / ключи у сейфа | последний кадр с кассиром | ключи — да |
| `EXIT` | Ноутбук и стол → до ухода | После ухода ноутбук открыт; деньги, журнал или сумка на столе | последний кадр с кассиром | нет |
| `DOOR` | Дверь закрыта → до начала работы | Только при **наблюдаемом входе**: после того как дверь открылась, она больше стабильно не закрывается | первый устойчивый момент «открыто» | нет |
| `PERSONAL` | Личных вещей на столе нет → пока идёт работа с деньгами | Личная вещь рядом с деньгами дольше ~1 с, **когда кассир один** (во время визита это обычно вещи клиента) | начало | нет |

Не реализовано:
- `NOCOUNT` — деньги в сейф без пересчёта; нужны состояния машинки, см. §9;
- `REJECT` — отбракованные купюры смешаны без проверки;
- `THIRD` — чужое удостоверение;
- частичный возврат денег клиенту.

Уточнения:
- **`SAFE` при пересчёте:** при приёме денег сейф открывают, когда пачка ещё в машинке, и это нормально. Поэтому требование — машинка пуста в момент открытия сейфа.
- **`DOOR`:** кассира часто видно сквозь стекло ещё до открытия двери, поэтому «закрыто» до открытия не считается закрытием после входа.

## 7. Выход

`DetectedEvent(type_code, timecode_sec, description, evidence[1–3], needs_review)`. Моменты-доказательства — кадр нарушения и кадры примерно за 0,6 с до и после. Описание — что видно, без юридических утверждений, например: «Кассир покидает рабочее место, ноутбук остаётся открытым.» Вердикт: `violation`, если есть хотя бы одно событие.

## 8. Результаты (детектор v4, разметка организаторов)

Метки дают вердикт и один таймкод на ролик, без типа. Поэтому проверяется вердикт и время ближайшего события.

| | train (25 роликов) | validation (9) |
|---|---|---|
| Верный вердикт | 76% | 44% |
| Пропущено нарушений | 2 из 14 | **0 из 4** |
| Ложных тревог | 4 из 11 чистых | 5 из 5 чистых |
| Таймкод в пределах 3 с | 4 из 12 | 3 из 4 |

Примеры совпадений таймкодов с метками удалены из публичной копии (они раскрывают разметку роликов).

Источники ложных тревог:
1. **Ноутбук «открыт» при уходе.** «Выключил» может значить «экран погас, крышка открыта»; по крышке сверху это не определить. По крышке сверху это не определить.
2. **ID «только после денег».** Ровно конфликты разметки из Aibar.md (ID не упомянут в описании), плюс `id_card` срабатывает на деньгах.
3. **Разрыв визита:** одна пропущенная рамка человека даёт ложные `INCOMPLETE`/`TABLE`.
4. **`PERSONAL`** в роликах с отбраковкой купюр: вероятно, UV-детектор или отбракованные купюры распознаны как личная вещь.

Пропуски на train: частичный возврат денег (не реализован) и дверь, которую детектор кратко видит «закрытой».

## 9. Что нужно от модели следующего шага

Ниже — по убыванию пользы для правил.

1. **Трекинг людей со стабильными ID и ролями (кассир / клиент).** Сейчас роль выводится из числа людей, и одна пропущенная рамка ломает визит. Нужно:
   - ID трека, переживающий кратковременные пропуски;
   - роль по стороне стола относительно машинки и ноутбука;
   - события «клиент вошёл/вышел».
2. **Состояния счётной машинки:** пусто / деньги сверху (подающий лоток) / деньги снизу (приёмный лоток) / отбраковка. Это даёт `NOCOUNT` (деньги не прошли машинку), «взял сверху, а не снизу» и `REJECT`.
3. **Точность `id_card`.** Сейчас ID часто путается с деньгами, и правило `ID` теряет смысл в обе стороны. Нужны примеры ID в руке и с ракурса сзади.
4. **Владение деньгами:** чья пачка — клиента A или B, посчитанная или нет. Без трекинга пачек `TABLE` и смешивание определяются только косвенно.
5. **Состояние ноутбука:** экран включён/выключен, а не только крышка. Иначе правило ухода остаётся спорным.
6. **Ключи** — мелкий объект, сейчас почти не находится. Возможно, нужен кроп вокруг замка сейфа.
7. **Отражения людей в стекле** — отдельный класс `reflection` или отсев трекером: отражение движется синхронно с реальным человеком.

Если трекер будет выдавать в JSON `track_id` и `role` для людей и пачек, правила перейдут с подсчёта людей на треки без изменения остальной логики.

## 10. Вопросы на ревью

1. Подход «дедлайн = событие» без таймеров — согласны, или для каких-то правил нужен порог (например, «дверь открыта дольше N секунд»)?
2. Ноутбук при уходе: считать нарушением только явно открытую крышку или отправлять на review? Это вопрос регламента, а не модели.
3. Должен ли кейс «ID увидели после передачи денег» быть нарушением или review? Это влияет на несколько роликов с конфликтующей разметкой.
4. Роли: можете ли вы дать роль трека (кассир/клиент) на своей стороне, или определять её здесь по геометрии?
5. Каких событий трекера не хватает в формате JSON, чтобы заменить эвристику `people`?

## 11. Как запустить

```bash
# детекции по роликам (GPU)
python training/infer_video.py --weights runs/v4/checkpoint_best_total.pth --videos ~/open/videos/X-*.mov --out runs/v4/det_all
# правила против разметки (CPU; test-ролики пропускаются)
python training/eval_rules.py --detections runs/v4/det_all --labels ../open/open_labels.xlsx
# таймлайны сигналов для отладки
python training/rule_timelines.py --detections runs/v4/det_all --videos <clip>,<clip>
# в сервисе: PIPELINE=real, DETECTOR_WEIGHTS=/models/detector/checkpoint_best_total.pth
```
